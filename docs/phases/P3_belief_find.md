# P3: Belief-Find (BP-guided UF) + Iteration-Budget Study

**Time box:** 0:45  **Depends on:** P1, P2  **Headline result**

## Goal
Combine P1 and P2: run BP for `k` iterations, turn its beliefs into new edge weights, and run weighted UF on the re-weighted graph. Then run our **novel contribution**: a study of how accuracy and latency change with the BP iteration budget `k`, plus a fast path that skips UF whenever BP already converged.

> **Credit:** "belief-find" was introduced by Higgott et al., PRX 13, 031007 (2023). We implement it from scratch. The iteration-budget and fast-path latency study is our addition. Also cite Caune et al., arXiv:2306.17142 (BP as a partial decoder) when presenting the fast path.

## Concept primer (tell the human this before coding)
UF on its own treats every fault as having its fixed prior probability. BP has looked at *this particular syndrome* and has an opinion: "that edge over there is probably the culprit." BP doesn't need to be right. It only needs to hand UF a better map. We lower the weight of edges BP suspects and raise the weight of edges BP clears, then let UF do what it's good at.

The extra trick: on many shots BP alone already explains the syndrome perfectly. On those shots we can skip UF entirely, which is a fast path. The real-time question is: **how few BP iterations do we need to get most of the benefit?** Fewer iterations means lower latency on hardware.

**Prediction exercise:** *"Will 2 BP iterations get us most of the gain, or do we need 30?"*

## Algorithm
```
pred_bp, converged, Λ = BP(H, priors, syndrome, max_iter=k)
if fast_path and converged:      return pred_bp
q_j   = 1 / (1 + exp(Λ_j))                       # posterior error prob per mechanism
p_e   = XOR-combine q_j over mechanisms j that contain edge e  (via mech_to_edges)
        # XOR rule: p ← p(1−q) + q(1−p)  (same rule as parallel-edge merge)
w_e   = ln((1 − p_e) / p_e)   (clamped)
return WeightedUF(graph with weights w_e, syndrome)
```

## Agent notes
- If belief-find does **not** beat UF, check in this order: (1) LLR sign convention, (2) whether `mech_to_edges` maps to the right edges, (3) whether the weight clamp is too aggressive, (4) whether there's enough shots. Don't tune until the k=0 test passes.
- BP posteriors on *converged* shots can be extreme (±50). Clamp `q` to [1e-12, 1 − 1e-12] before taking logs.
- For the k=0 test to be bit-for-bit, the re-weighted UF must reuse the **same fixed integer `scale`** as the base graph. Don't recompute the scale from each shot's new weights.
- Keep the fast path optional, because the k-sweep needs it off to measure the pure re-weighting gain.
